## 2. PLANO

**Arquivo:** `D:\recapd-ambientes\producao\bin\anime_fetch.py` (linha 451-452)

**O que sai:**
```python
# Tenta apenas "tiny" para minimizar risco de MemoryError
for msize in ("tiny",):
```

**O que entra:**
```python
# Tenta tiny primeiro; se texto curto/vazio, tenta base (mais preciso em áudio com ruído/música)
for msize in ("tiny", "base"):
```

**Lógica após a mudança:**
1. Tenta primeiro `tiny` (rápido, baixo uso de RAM)
2. Se tiny retornar <50 chars → loop continua e tenta `base` (mais preciso)
3. Se base também falhar → retorna None (como hoje)

**Teste pós-mudança:**
Não vou rodar nada agora (etapa só de diagnóstico), mas o dono deve testar com:
- Vídeo curto do estoque (como o vR1tN9TtiOc que deu 16 chars hoje)
- Verificar no log se aparece: `[fetch] Whisper transcreveu (model=base, ...)`

## 3. RISCO

**Risco médio-baixo:**
- **Uso de RAM aumenta:** modelo `base` consome ~1 GB vs ~400 MB do `tiny`
  - Mitigação: só roda se tiny falhar (maioria dos vídeos nem chega no base)
- **Tempo de processamento aumenta:** base leva ~2-3x mais que tiny
  - Mitigação: só penaliza vídeos que tiny já estava falhando (hoje abortavam de qualquer forma)
- **Timeout pode precisar de ajuste futuro:** se base der timeout em vídeos longos
  - Mitigação: timeout dinâmico atual (900s-7200s por duração) deve cobrir

**Como desfazer:**
Reverter linha 452 de volta para `for msize in ("tiny",):` — uma linha, zero risco de quebrar outra coisa.
